# XR Backend (real, tested)

Node.js >= 22.5, **zero external dependencies** (`node:sqlite`, `node:crypto`, `node:http`, `node:test`).

    npm test          # runs all integration tests against a real HTTP server + real SQLite
    npm run dev       # starts on :3000, DB file ./data/xr.db

Auth: `POST /auth/login` -> use `Authorization: Bearer <sessionId>`.

## Status (verified by tests in /tests — 152/152 passing)
- Stage 11 Observability + Payment Adapter (Phase 9 — Airtel Money / MTN Mobile Money / Card): `GET /health` (liveness) and `GET /ready` (readiness — actually queries the DB, not just "process is up"), both unauthenticated by design. Every response carries an `X-Request-Id` header; every request is logged as one structured JSON line (`src/lib/logger.js`) with a `SENSITIVE_KEYS` redaction allowlist so a password/token/session-id/signature can never end up in a log line even nested inside a logged object. Payment adapter follows the exact same provider-independent pattern as WhatsApp: `PaymentProvider.initiatePayment({method,network,amount,currency,phone}) -> {providerReference,status}` / `verifyWebhookSignature({rawBody,signature,secret}) -> boolean`; `MockPaymentProvider` simulates all three rails with no network call; `RealPaymentProvider` is a placeholder that explicitly throws `BLOCKED_PENDING_PROVIDER` on every method — swapping to a real integration is writing new provider classes (realistically one per rail, since Airtel Money and MTN MoMo are different real APIs) and flipping `businesses.payment_provider` from `MOCK` to `REAL`. `payment_intents` (pre-sale) is deliberately separate from `payments` (post-sale) so a provider-confirmed SUCCESS is never lost even if sale creation fails afterward — `GET /payments/unreconciled` (Manager/Owner only) finds exactly those orphaned SUCCESS rows, and `POST /payment-intents/:id/attach-sale` reconciles one to a sale by hand. Idempotency is two-phase: the idempotency key is claimed with an `INITIATED` row *before* the provider is ever called (verified under a real concurrent-request test — exactly one row survives), and the provider call itself happens outside any open DB transaction, since a SQLite write-lock must never be held across an awaited network call. Webhook delivery is HMAC-SHA256 signed and verified before any business logic runs; a `payment_webhook_events` table (`UNIQUE(provider, provider_event_id)`) makes a retried webhook delivery an idempotent no-op instead of double-applying a status change — both the forged-signature and the replayed-event cases are covered by tests, not just the happy path
- Stage 10 Notifications/WhatsApp (Phase 8): provider-independent `WhatsAppProvider` adapter (`send({to,from,type,body}) -> {providerMessageId,status}`); `MockWhatsAppProvider` simulates real delivery with no network call; `RealWhatsAppProvider` is a placeholder that explicitly throws `BLOCKED_PENDING_PROVIDER` — swapping to real delivery later is a one-class implementation + flipping `businesses.whatsapp_provider` from `MOCK` to `REAL`, nothing else changes. Queue -> SENDING -> SENT/RETRYING/FAILED (max 3 attempts), a FAILED delivery never rolls back the sale that triggered it, `whatsapp_sender_number` is a placeholder column ready to hold a real number once supplied. A lightweight in-process worker (`startNotificationWorker` in server.js, polls every 3s) stands in for real queue infrastructure (documented limitation — no Redis/job-runner exists). Found & fixed during testing: an initial auto-fire-on-queue + self-rescheduling-retry design made delivery timing non-deterministic (a real race condition, now replaced with explicit `processQueue`/`attemptDelivery` calls) — kept here as an honest record, not smoothed over

- Stage 9 GPC Import Engine (Phase 4) + QR/Barcode Lookup (Phase 5): a real validate/dry-run/commit import engine (hierarchy consistency, duplicate-code detection, idempotent version names, only a fully-valid version becomes ACTIVE, old versions never deleted/overwritten) — tested against an explicitly-labeled TEST FIXTURE (NOT real GS1 data, since no actual dataset has been supplied yet, only release notes). Products default to `gpc.status: UNMAPPED` and classification against an unknown brick code is rejected, never guessed. `GET /products/lookup?code=` resolves by barcode, SKU, or internal ID, tenant-scoped, 404 (not a leak) across businesses. GPC import is Owner-only (global/platform-level action — see docs/product/OPEN_DECISIONS re: a dedicated platform-admin role). Found & fixed: `audit_logs.business_id` was NOT NULL, which broke audit logging for this genuinely cross-business action — now nullable

- Stage 8 Tax / Discounts / Price Override (Phase 3): effective-dated tax configs (0% if none configured — never fabricated), line- and sale-level discounts (percent/fixed, negative-total blocked, requires `sale.discount` permission — Cashier does NOT have it), price overrides below-min/above-max (requires `price.override.below_min`/`above_max`, Cashier does NOT have either; every override writes a `price_overrides` row with standard/min/max/requested/final price + reason + approver). Finance now reports Revenue as tax-EXCLUSIVE (`taxable_amount`), with `taxCollected` reported separately, since collected sales tax isn't business revenue. Found & fixed during testing: Manager was missing `sale.write` (couldn't process authorized overrides themselves) and a `permission_used` CHECK-constraint bug that silently 500'd every override — both caught by the test suite, not shipped silently

- Stage 7 ASVS Security Hardening: built against the REAL OWASP ASVS 5.0.0 PDF (previous upload was a mismatched risk-assessment workbook — now corrected, see docs/standards/STANDARDS_INVENTORY.md). Added: minimum 8-char password policy (6.2.1), password change endpoint requiring current password (6.2.2/6.2.3), optional "revoke all other sessions" after a password change (7.4.3). Full evidence-based matrix in docs/security/OWASP_ASVS_MAPPING.md — nothing marked IMPLEMENTED without a cited test

- Stage 6 Supplier Returns / Damage / Loss / Adjustments / Sessions / Rate Limiting / Reports: supplier returns and damage/loss/adjustment-in all reuse the same FIFO ledger logic as sales (no second inventory engine); every adjustment requires a reason; session listing + per-session revocation; login rate-limited to 5 attempts / 15 min per email (429 RATE_LIMITED, in-memory — multi-instance deployment needs a shared store, see code comment); filterable Sales/Purchases/Inventory/Returns reports, each row linking back to its source ID

## Known limitations (honest)
- SQLite + single Node process: concurrency safety comes from synchronous DB access inside one transaction (`BEGIN IMMEDIATE`). Moving to PostgreSQL / multiple processes REQUIRES row-level locking (SELECT ... FOR UPDATE) and re-running the concurrency tests against it.
- The sale-level `payment_method` field (Cash/MobileMoney/Bank/Card/Other, recorded at POS) and the Stage 11 `payment_intents.method` field (MobileMoney/Card, the actual Airtel/MTN/Card provider adapter) are two separate concepts today — a POS sale is not yet auto-linked to a payment intent; `POST /payment-intents/:id/attach-sale` does that linking explicitly/by hand. Wiring POS checkout to initiate a payment intent automatically for non-cash sales is a natural next step, not yet built.
- Login brute-force protection (rate limiting) is in-memory and fixed-window — fine for one instance, not multi-instance-safe (documented in code).
- Session inactivity timeout (ASVS 7.3.1/7.3.2) is PARTIAL: only a 24h absolute session lifetime exists, no idle timeout yet.
- Errors use RFC 9457 `application/problem+json` shape throughout.
